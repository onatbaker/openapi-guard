# openapi-guard

A CLI tool that compares two OpenAPI spec files and reports breaking changes. Run it locally or drop it into CI to catch contract breakage before it hits production.

## Why

OpenAPI specs drift. A field gets renamed, an enum value gets removed, a required parameter gets added — and the clients that depend on that contract break silently. Code review catches some of it. This catches the rest.

## Install

Download a binary from the [releases page](https://github.com/onatbaker/openapi-guard/releases) for your platform, or build from source:

```
go install github.com/onatbaker/openapi-guard/cmd/openapi-guard@latest
```

## Usage

```
openapi-guard diff --old old.yaml --new new.yaml
```

Output defaults to text. Pass `--format json` to get machine-readable output.

## Example

Given two versions of a spec where fields were removed, types changed, and a required parameter was added:

```
BREAKING: GET /health removed
BREAKING: GET /users/{id} 200 response field 'id' is no longer required
BREAKING: GET /users/{id} added required query param 'currency'
BREAKING: GET /users/{id} changed 200 response field 'name' type string -> integer
BREAKING: GET /users/{id} narrowed enum for 200 response field 'status'
BREAKING: GET /users/{id} removed 200 response field 'address.street'
BREAKING: GET /users/{id} removed header param 'X-Tenant-ID'
BREAKING: POST /users added required request body field 'role'
WARNING: GET /users/{id} removed 404 response field 'code'
WARNING: GET /users/{id} removed 422 response
INFO: GET /healthz added
```

The exit code is 1 if there are any breaking changes, 0 if clean.

## What it detects

**Endpoints**: removed endpoints are breaking. Added endpoints are info.

**Parameters**: removed parameters are breaking. Required parameters added are breaking. Optional parameters added are info. Type changes and enum narrowing are breaking.

**Request body**: required fields added or removed are breaking. Type changes, enum narrowing, and required promotions are breaking. Nested fields are tracked with dotted paths (`address.street`).

**Responses**: 200 field changes are breaking. 4xx/5xx field changes are warnings, since error shapes are handled more loosely by clients. Removed response codes follow the same split: a removed 2xx is breaking, a removed 4xx/5xx is a warning.

## Severity levels

- **BREAKING** — a client built against the old spec will fail
- **WARNING** — likely a problem, but clients may handle it gracefully
- **INFO** — additive change, no existing clients affected

## GitHub Action

Add this to any workflow to block PRs that introduce breaking changes:

```yaml
steps:
  - uses: actions/checkout@v4

  - name: Check for breaking API changes
    uses: onatbaker/openapi-guard@v0.1.0
    with:
      old-spec: specs/old.yaml
      new-spec: specs/new.yaml
```

The action exits non-zero on breaking changes, which fails the check.

### Using a generated spec

If your spec is generated from code (FastAPI, Django, ASP.NET, NestJS), generate it as a step before running the diff. For FastAPI:

```yaml
- name: Generate spec
  run: python scripts/export_openapi.py > specs/current.yaml

- name: Check for breaking API changes
  uses: onatbaker/openapi-guard@v0.1.0
  with:
    old-spec: specs/main.yaml
    new-spec: specs/current.yaml
```

The common pattern is to commit the spec from main to the repo and compare against a freshly generated one from the PR branch.

## Framework compatibility

Tested against specs generated by FastAPI (OpenAPI 3.1), Django/drf-spectacular (OpenAPI 3.0), ASP.NET/Swashbuckle (OpenAPI 3.0), and NestJS/@nestjs/swagger (OpenAPI 3.0).

FastAPI and other OpenAPI 3.1 generators use `anyOf: [{type: string}, {type: null}]` for optional fields instead of `nullable: true`. openapi-guard handles this correctly — those fields are not invisible to the diff.
